## 修復計畫

### P0 — 恢復活動前後端契約（已完成）

1. 以目前最新來源為基礎，只恢復「預計結束時間」的介面與資料送出：建立、修改、複製、公開卡片、邀請頁與營運總覽。
2. 恢復營運狀態 `進行中`，並依「進行中 → 即將開始 → 已結束／已取消」排序。
3. 加入前端驗證：結束時間必填、同日、晚於開始時間；避免只得到泛用的 `Failed to fetch`。
4. 將前端快取版本一起更新，避免 Brave／Chrome 讀取舊活動表單。
5. 完整測試必須回到 62/62，並確認建立與複製活動的 CTA 在桌面、手機均維持置中與間距。

### P1 — 讓結束狀態不依賴有人開頁面

1. 將 `closeElapsedEvents` 接入既有排程工作，每 5 分鐘執行一次；保留目前 API 讀取時的即時檢查作雙重保護。
2. 排程只更新仍為 `active` 且已超過結束時間的活動，保留活動、報名、LINE 綁定與提醒歷史。
3. 新增回歸測試：無任何訪客讀取時，排程仍能把逾期活動改為 `completed`。

### P2 — 發布與維護護欄

1. 在發布前比對活動表單與 API 所需欄位，將 `endTime` 視為不可被來源同步移除的契約。
2. 每次發布都更新本檔、[Changelog](../Changelog.md) 與回憶膠囊的獨立進度檔（若該次有影響）。
3. 發布後只以 [GitHub Pages 正式入口](https://bfc8g4v63.github.io/) 驗證公開使用流程；不將內部承載來源作為使用者入口。

## 下一個執行順序

1. 實作 P1 排程自動結束、加入測試，再統一發布。
2. 發布前持續檢查來源同步差異，避免活動表單契約再次被回退。

## 驗收條件

- 建立或複製活動時一定能填寫並送出結束時間。
- 結束時間一過，活動顯示為「已結束」、停止新報名，且在營運管理歷史區出現。
- 即使沒有任何人開啟網站，最晚在排程週期後也會完成狀態更新。
- 完整測試全數通過，既有活動、LINE 綁定、提醒、回憶膠囊資料與私有 R2 存取不受影響。
